# 2026-11 变更说明（护栏 / 任务闭环 / 控制台）

这一轮从「本地小模型能不能用」开始，最后落成了三层东西：**写操作的确定性护栏**、**任务通知闭环**、**控制台的可用性**。设备端联调时这份文档够用来对接口和避坑。

对应提交：`a4552d9` … `e84efa4`（12 个），测试从 154 涨到 214。

---

## 一、为什么要做护栏

用 Spark-X2.6-4B（本地）和 aisp 的 DeepSeek-V4.1-Flash 跑同一组用例，暴露的问题不是「答得不好」，而是**写错数据**：

| 现象 | 实测 |
|---|---|
| 凭空补到期日 | 「冰箱里还有三个鸡蛋」约一半概率被记成今天/12-21/12-31 到期 |
| 相对日期算错 | 「牛奶下周三过期」4B 稳定算成周四（正确是 11-25） |
| 查询被当成写操作 | 「我家水费户号是多少」调用 `task_add`，造出一条不存在的交电费提醒 |
| 假确认 | 没调任何写工具，却回「已经记在清单里了」，库里一条都没有 |

提示词约束不住（在系统提示里写「查询不得顺带写入」，重跑三次照旧），所以改成**编排层的确定性校验**。

## 二、五道防御（对所有模型生效，除注明外）

| # | 机制 | 位置 | 作用 |
|---|---|---|---|
| 1 | 中文日期解析 | `agent/dates.py` | 「明天/下周三/三天后/周末/11月25日/下午三点」→ 具体日期，交给代码算 |
| 2 | 写参数护栏 | `agent/guard.py` | 日期以原话为准；句子无日期线索则留空；`task_add` 标题在原话里找不到依据则整次拒绝 |
| 3 | 参数校正提示 | `agent/guard.py` `correction_note` | 把校正结果附在工具返回里，减少模型口播旧值 |
| 4 | 写操作确认 | `agent/confirm.py` | `CONFIRM_WRITE_ACTIONS` 控制，复述参数后再落库（默认关闭） |
| 5 | 假确认拦截 | `agent/guard.py` `guard_false_claim` | 非疑问句 + 无写工具执行 + 回复声称已完成 → 换成诚实说法 |

设计取舍：第 1–3 条无条件生效，换模型时行为不变；代价是偶尔用代码判断覆盖模型，所以日期线索词表要持续补（「年底/过几天/周末」等 12 个是踩出来的）。

### 配置

```
CONFIRM_WRITE_ACTIONS=0        # 关闭（默认，大模型直接用）
CONFIRM_WRITE_ACTIONS=1        # 四个写工具全部先确认
CONFIRM_WRITE_ACTIONS=tasks    # 只确认 task_add（误提醒代价最高）
CONFIRM_WRITE_ACTIONS=item_add,task_add   # 显式列表
```

开启后同时启用第 5 条。**决定用本地模型时必须打开**，否则写操作等于裸奔。

## 三、任务通知闭环

### 新增工具

| 工具 | 语义 | 备注 |
|---|---|---|
| `task_update` | 改标题/时间/类型 | 至少改一项；标题须在原话里有依据 |
| `task_cancel` | 标记 cancelled，不删记录 | 保留审计 |
| `task_postpone` | 改到指定日期 | **「明天」「下周一」是目标日期，不是「到期日 +N 天」**；说不出具体日期才退化成顺延 N 天 |

⚠️ 第 3 条的语义是实测后修正的：第一版把「明天」当成 +1 天，结果把「明天到期」的任务推到了后天。

### 接口

```
POST /api/tasks/{id}/postpone   {"days": 1}   →  {"ok": true, "task": {...}}
```

延期必须**清 `reminded_at` 并把 status 退回 `pending`**，否则冷却窗口会挡住，延期后再也不提醒（`Tasks.postpone` 已处理）。

### 提醒卡片

页面在线时，SSE 的任务提醒渲染成卡片，带「完成 / 延期一天 / 取消」三个按钮，直接打上面的接口。

- 按钮不持久化：聊天历史只存文字（和语音播放按钮一致）
- **Web Push 仍是纯文字**：推送正文不发交互，从系统通知点进来看到的是文字版本

### 澄清规则修正

「交电费的提醒不用了」原来会被澄清引擎拦住，反问「是哪里的电费」，导致**取消电费提醒永远走不通**。现在取消类说法（不用了/取消/算了…）直接放行，新建账单仍然会追问。

## 四、数据正确性

### 同名物品合并

`item_add` 的去重只在 5 分钟提案窗口内、且名称+日期都要一致。一周里说两次「牛奶下周三过期」会变成两条记录、两次提醒。

现在 `ProposalService.add_item` 合并同名物品：

| 情况 | 行为 |
|---|---|
| 带新日期 | 更新到期日，清 `reminded_at`、状态退回 `active` |
| 不带日期 | 保留原值，不抹掉已知日期 |
| 已经过期 | 不动旧记录，新建一条（保留历史） |

审计里记为 `merged`。

### 记忆检索兜底

`memories_fts` 只索引 `summary`，原文独有的词（号码、品牌、补充说明）查不到，助手会回「我没记过」——其实记过。

现在 FTS 未命中时用 `LIKE` 扫 `summary + text` 补召回，`%` 和 `_` 已转义。实测漏召的 `0571`、`南孚`、`贴在门口`、`每周三` 全部恢复。

## 六、已知限制

1. **4B 口播旧值**：落库数据正确，但模型仍可能照着旧参数说话（库里 11-25，嘴里 11-26）。`correction_note` 只能缓解，不能保证。
2. **假确认不能 100% 拦截**：规则是保守的（疑问句、无写工具、有完成表述），边界场景仍会漏。
3. **Web Push 无交互**：要按钮只有页面在线那条路径。
4. **多轮指代弱**：本地 4B 对「那还剩几天」这类指代会反问，aisp 正常。
5. **日期线索词表是穷举**：没收录的说法会被当成「没有日期线索」，护栏会清空模型给的日期。遇到误伤就往 `agent/dates.py` 的 `_DATE_HINT_RE` 里补。

## 七、给设备端的注意点

- 语音入口建议只暴露：`family_search`（查）、`task_add`（记提醒）、`task_complete` / `task_postpone` / `task_cancel`（操作提醒）
- 写操作一律走确认（本地模型开 `CONFIRM_WRITE_ACTIONS=1`），客厅场景一句「要记成…确认吗」比事后纠错便宜
- 延期的说法直接传原话即可，天数由服务端换算，不要让设备端算日期
- 若将来做 aisp → 本地自动降级：**降级时必须同时切弱模型模式**（D29）

## 八、2026-11-23：对外话术统一（`agent/wording.py`）

写操作的三处文案——确认句、确认后的回话、执行回显——原来各写一遍，日期格式不一致。
最难看的是确认之后：回话直接用了工具返回的原始串

```
已添加物品：牛奶，到期日 2026-12-02
```

TTS 会念成「二零二六 杠 十二 杠 零二」。确认的意义是让人当场发现参数错了，
念成一串数字等于没确认。

现在统一由 `agent/wording.py` 生成：

| 场景 | 现在说的话 |
|---|---|
| 写入确认 | 你说的「牛奶下周三过期」，要记成：牛奶，12月2日（周三）到期。回复「确认」或「取消」。 |
| 确认之后 | 已记好：牛奶，12月2日（周三）到期。 |
| 直接写入的回显 | 牛奶，12月2日（周三）到期。（只在参数里有日期、且模型回复没提到时补） |

三条规则：日期说「12月2日（周三）」或「明天」，有时间说「下午3点」不说「15:00」，
确认句引用用户原话（人记得自己说了什么，比记得参数格式可靠）。

顺带修了一个**会随时间变红的测试**：`test_confirm_writes_and_keeps_guarded_args`
把「下周三」写死成 `2026-11-25`，换一天跑就失败（今天是 11-23，下周三其实是 12-02）。
改成用 `parse_date_text` 现场推算。

测试 266 → 280。真模型实测：

```
问：牛奶下周三过期（确认模式）
   你说的「牛奶下周三过期」，要记成：牛奶，12月2日（周三）到期。回复「确认」或「取消」。
确认后：已记好：牛奶，12月2日（周三）到期。
库里：牛奶 2026-12-02
```

## 九、2026-11-23：删除只删该删的（`Items.delete_exact` / `_resolve_delete`）

`item_delete` 原来是 `LIKE %名字%` 之后**全删**：清单里同时有「酸奶」和「酸奶机」时，
说一句「删掉酸奶」会把两台机器都删掉。删除不可逆，这种模糊匹配迟早出事。

现在删除前先坐实目标（`assistant._resolve_delete`）：

| 情况 | 行为 |
|---|---|
| 有精确同名 | 直接确认「确认删除物品「酸奶」吗」 |
| 只命中一条相似项 | 用它的全名确认（「牛奶」→「蒙牛牛奶」），用户能看出认错了 |
| 命中多条 | **不删**，列出名字问要删哪个，直接结束本轮 |
| 一条都没有 | **不删**，明说「没有找到，什么都没删」 |

后两种情况刻意不把结果交回模型转述——它会顺势说成「已经删掉了」。
记忆删除同理：零命中不进确认，多条命中在确认句里报条数。

真模型实测（清单里有 酸奶 / 酸奶机 / 酸奶大瓶）：

```
删掉酸奶 → confirm：确认删除物品「酸奶」吗？回复「确认」或「取消」。
删掉牛奶 → chat：没有找到「牛奶」这个物品，什么都没删。
清单：酸奶大瓶、酸奶机、酸奶   ← 一个都没少
```

测试 282 → 292。

## 十、2026-11-23：记忆摘要只能用原话里的字（`summary_grounded`）

记忆存「原文 + 摘要」，摘要进 FTS 索引。工具描述原来让模型「相对时间转绝对日期」，
于是实测出现：

```
原话：明天买电池
摘要：8月9日买电池      ← 模型自己换算的日期，还错了
```

`is_grounded` 拦不住它——判据是「至少一个二元组重合」，两句共享「买电」「电池」。
它适合判断「这个话题用户提过没有」，不适合判断「这句话是不是原话剪出来的」。

现在摘要用**子序列判据**（`agent/guard.py` 的 `summary_grounded`）：摘要里的每个字
都必须能在原话里按顺序找到，允许跳过字。摘要的本职就是把原话剪短，所以「只删不加」
就是它的定义。校验不过时：

| 处理 | 原因 |
|---|---|
| 摘要换成原话，**记忆照记** | 记忆是用户的真实陈述，摘要是可降级的 |
| 工具返回附一句校正说明 | 免得模型接着口播那个编造的日期 |

不拒收整条记忆：为了模型的格式错误丢掉用户的真实事实，是本末倒置。摘要变长只影响
索引体积，FTS 全文召回反而更好。

真模型实测（摘要都是原话剪出来的，没触发降级）：

```
原话：上周六去医院复查血压，医生说还行
摘要：上周六复查血压，医生说还行      只删不改=True
```

测试 292 → 298。

## 十一、2026-11-23：回复发出前过事实校验（`agent/verify.py`）

护栏和 `correction_note` 保证的是**库里**对，用户听到的却是模型那一句。实测模型能在
同一个回复里一边写对一边念错：参数校正成 12-02，嘴里仍说「11月25日过期」；
或者说成「12月2日（周四）」（那天是周三）。语音没有回看的机会。

现在最终回答发出前过一遍 `verify_reply`：

| 回复里的内容 | 判据 |
|---|---|
| 具体日期（12月2日 / 12月2号 / 2026-12-02） | 必须是这次写进去的那天（今天是例外，允许用作上下文） |
| 相对词（明天/后天…） | 换算成日子后再比 |
| 周几（下周三） | 带「下/本/这」的按整句解析，比具体日期 |
| 周几（周三） | 只比星期几——口语本来就会省「这周」 |
| 引号里的名字（「酸奶」） | 必须在用户原话或工具参数里出现过 |

不一致就**整句**换成 `wording.written_sentence` 拼的模板句，不修补也不拼接——
一段话里一句对一句错，比整句朴素更难发现。

配套改了两处：

1. **写完之后那轮不走流式。** 逐字推给设备的片段收不回来，校验失败也没法纠正。
   有写入时最终回答等校验完再一次性下发，第一轮（只吐 tool_calls）仍然流式。
2. **改期保留原时刻。** 真模型探针发现「取快递改到后天」把 15:00 改成了 00:00，
   模型却还说「下午3点」——库错了，校验再准也救不了。`domain/tasks.py` 的
   `_keep_clock`：只给日期时沿用原时刻，原话带了时间才覆盖。

真模型实测（第二轮回答故意换成错日期）：

```
模型原话：好，记好了，牛奶后天就过期。
实际回复：已记好：牛奶，12月2日（周三）到期。
库里：牛奶 2026-12-02
```

正常路径不误杀：

```
牛奶下周三过期   → 牛奶，12月2日（周三）到期。记好了，牛奶12月2号（下周三）过期…
明天下午三点取快递 → 取快递，明天下午3点。好，明天（11月24日）下午三点提醒你取快递。
取快递改到后天   → 取快递已经改到后天（11月25日）下午3点了。   库：2026-11-25T15:00
```

测试 298 → 317。

## 十二、2026-11-23：事实留失效史（`Facts.store` / `valid_to`）

`facts` 表一直有 `valid_from` / `valid_to` 两列，但从来没用过：`store` 每次都直接
`INSERT` 新行，旧行既没关闭也没删除。于是同一个户号存过几次就有几条「当前有效」，
检索时新旧值一起返回，模型挑哪条看运气。真实库里的样子：

```
id=1 爸妈家·电费户号 123456  valid_to=NULL
id=4 爸妈家·电费户号 123456  valid_to=NULL
id=5 爸妈家·电费户号 123456  valid_to=NULL
id=6 爸妈家·电费户号 123456  valid_to=NULL
```

现在：

| 情况 | 行为 |
|---|---|
| 值没变 | 沿用现有记录，不堆行（重复说同一件事很常见） |
| 值变了 | 旧行 `valid_to=现在`，新行 `valid_from=现在`，返回 `replaced` 让回话能说「原值已失效」 |
| 检索 | 默认只返回 `valid_to IS NULL`；`include_history=True` 或 `history(subject, predicate)` 看历史 |
| 旧库 | 启动时 `_close_legacy_duplicates` 把同主体+属性的多条有效记录关到只剩最新一条，幂等 |

不选「直接覆盖」：覆盖之后「以前是多少」就查不到了，而户号、地址、型号恰恰会变。
也不选「只插新行」——那正是现在的问题。

在真实库的副本上验过：6 行 → 3 条有效（爸妈家 / 家 / 户号 三个不同主体）+ 6 条历史；
再存一次新值，有效数不变、历史变 7。

测试 317 → 321。

## 十三、2026-11-23：MCP 接入点，`_meta` 声纹透传实测通过

### 先纠正一个方向

之前 ROADMAP 里写的是「写一个 `scripts/mcp_xiaoma.py`，出站连小智的接入点」。
读小智源码后确认方向**反了**：小智服务端才是 MCP 客户端，它出站连我们。

```
设备 ──语音──▶ xiaozhi-server ──MCP(WebSocket, 出站)──▶ 小马 /mcp_endpoint/mcp/
```

依据：`core/providers/tools/mcp_endpoint/mcp_endpoint_handler.py` 里
`websockets.connect(mcp_endpoint_url)`，然后发 `initialize` / `tools/list` / `tools/call`。

### 协议形状（按源码实现，没用官方 SDK）

- 裸 JSON-RPC 2.0，transport 是 WebSocket；`protocolVersion` 为 `2024-11-05`
- id 固定：`initialize=1`、`tools/list=2`、`tools/call` 从 3 开始
- 工具返回值只读 `result.content[0].text`，`isError: true` 表示失败
- 小智会忽略官方 SDK 的很多能力，用 SDK 反而要垫一层

新增 `adapters/mcp_endpoint.py`，`server.py` 加路由 `/mcp_endpoint/mcp/`：
只暴露一个工具 `ask_xiaoma(text)`，交给 `assistant.process_text`。

### `_meta` 透传：实测通过

小智把声纹识别结果放在 `tools/call` 的 `params._meta`：

```json
{ "speakerId": "spk-dad", "speakerName": "爸爸" }
```

未命中时整个 `_meta` 不出现。探针按同样的报文形状跑真实服务（不是 mock）：

```
① initialize → protocolVersion 2024-11-05
② tools/list → ask_xiaoma
③ tools/call → 你好呀！我是小马，家里的事都可以交给我记～
服务端日志：🔊 MCP 声纹身份：speakerId=spk-dad name=爸爸
```

不带 `_meta` 时日志没有这一行，会话落在 `mcp:device`；token 错误握手 403。

身份怎么用：**只分会话上下文**（`client_id = "mcp:<speakerId>"`），不认「这是谁」，
不参与鉴权，写操作照样走提案/确认。`speakerId → persons` 的归属留给 D40。

### 配置与文档

- `.env` 新增 `MCP_TOKEN`，留空则接入点整体关闭（它能写库，不能默认对外）

## 二十三、2026-11-23：事实检索拆词匹配（D46 落地）

`Facts.search` 原来是 `subject LIKE %query% OR predicate LIKE %query% OR value LIKE %query%`，
要求整串连续子串。存 `subject=水费 / predicate=户号`、查「水费户号」时，两列都不含这个
连续串，什么都查不到——而键和查询都是模型自己写的，词序一变就失效。

改法（方案一，最小改动）：

- `query` 拆成检索词：空白/标点分词，词长 > 2 再拆成二字组
- 每个词都要在 `subject || predicate || value` 里出现（**逐词 AND**）
- `%` `_` `\` 转义，用户的一个百分号不会捞出全表
- 不做同义改写：「账号」对「户号」仍然查不到，那是另一层

为什么不用「命中任一」：会把「自己家电费户号」的水费那条也捞出来，语音里念错户号
比查不到严重得多。逐词 AND 的结果是：说得越具体越准，说得不完整的就不返回。

顺带修正了对 D46 的误判：最初以为是「subject 要不要带家庭名」，实测带实体澄清的
正常写入路径本来就对齐（`subject=自己家 / predicate=水费户号`），问题只在检索。

评测集用例改成更真实的检查：两家各存一条水费户号，问「爸妈家的水费户号是多少」，
必须返回 12345678 且不能出现 11112222。**20/20**。

## 三十一、2026-11-23：评测突然 65 秒一条，根因是没走代理

|---|---|

## 三十四、2026-11-23：周期提醒（每天 / 每周 / 每月）

家庭里高频的提醒几乎都是周期性的：吃药、倒垃圾、接孩子、交房租。之前 `tasks` 只有
一次性，说「每天八点吃药」只能建出明天一条，后天就没了。

### 定了什么

| 问题 | 结论 |
|---|---|
| 支持哪些 | 每天 / 每周X / 每月X号；不做完整 RRULE，不做「工作日」「隔周」 |
| 没有时间 | 追问，不替用户定 |
| 什么时候响 | **到点才响**（`due <= now`），不提前 |
| 错过了 | 只补一次，然后滚到下一次 |
| 完成 | 跳过本次，周期继续 |
| 取消 | 整个系列停掉 |
| 改期 | 改下一次，锚点跟着走 |
| 月末 | 31 号遇到小月按当月最后一天 |

### 实现的三个关键点

1. **`recur` 列 + 旧库迁移**：`CREATE TABLE` 里带上，启动时 `PRAGMA table_info` 检查后
   `ALTER TABLE` 补列。现场 5 条老任务迁移后完好（`recur=''`）。
2. **领取即滚动**：周期任务到点被 `claim_due_reminders` 领取后，`due_at` 推到下一次并
   清 `reminded_at`。不清的话第二天的提醒会被 24 小时冷却挡住——这是最容易踩的坑。
3. **完成不标 done**：标了任务就从列表消失，用户会以为提醒没了。

### 解析（`agent/dates.py`）

「每天早上八点」在晚上八点说出来，下一次是明天——所以 `parse_recurrence` 算的是
**下一次**，当天时刻已过就顺延一个周期；周几、几号同理。每月 31 号在小月取最后一天。

### 措辞

确认句说「吃药，每天早上8点」，不说「明天早上8点」——周期任务说明天反而误导。
提醒文案是「提醒：吃药（每天）」，不说「今天到期」。

### 验收

评测新增 4 条（真实模型）：

| 用例 | 结果 |
|---|---|
| 每天早上八点提醒我吃药 | ✅ `recur=daily`，回「每天早上八点提醒你吃药，从明天开始」 |
| 每周三下午三点提醒我开会 | ✅ `recur=weekly`，第一次算到 11-25 |
| 每月1号早上九点提醒我交房租 | ✅ `recur=monthly`，第一次算到 12-01 |
| 每天提醒我吃药 | ✅ 追问「每天几点」，没有落库 |

第一次跑 **35/36**，挂的是老用例「提醒：清单」：模型用 `family_search` 而不是 `task_list`
回答「我有哪些提醒」，答案完全正确，是判据写死了工具名。系统提示本来就要求「家庭事务
查询用 family_search」，于是把用例放宽成两者皆可——这是判据问题，不是行为退化。

复跑 **36/36**，平均 7.0 s、最长 15.9 s。单测 405 → 424。

## 三十五、2026-11-24：同义改写（存「户号」，问「账号」也能查到）

D46 落地了「拆二字组、逐词 AND」，但把说法差异留在了外面：用户问「水费账号是多少」，
库里存的是「户号」，查不到。语音场景里同一个东西各家说法不同（账号/户号、煤气/燃气/
天然气），这类词应该互换。

### 只改检索侧，不改写库内容

- 写进库的仍是用户原话：「账号」就存「账号」，展示出来不会变成别的词
- `agent/synonyms.py` 维护规范词表与 `canonicalize`，`Facts.search` 把查询串和库里参与
  匹配的文本都换成规范词，再按原来的二字组逐词 AND 比
- `subject` / `predicate` 过滤同样走 `variants`，两个方向都能命中

事实表只有几十行，所以先从 SQL 取回、在 Python 里归一过滤，不再往 SQL 里拼 REPLACE：
规则只有一处，测试直接调 `canonicalize` 就能覆盖。

### 词表宁缺毋滥

收入：户号/账号、燃气/煤气/天然气、宽带/网费/宽带费、物业/物业费、水费/自来水费、
车牌/车牌号、身份证/身份证号、手机号/手机号码/电话号码。

不收入：「水费/水表」（读数和户号是两回事）、任何单字替换（「号」「费」放开会牵连
「型号」「水表费」）。原则是**宁可查不到，也不查错**：放宽一个检索词不会放松同一查询里的
其它词，「电费账号」不会把「水费户号」捞出来。

### 顺手修掉的跨午夜问题

同一天里 3 条 `test_verify` 变红：模板句把「明天」说成了「今天」。根因是
`verify_reply` 按调用方传入的 `today` 判断，`wording.written_sentence` 却自己取
`date.today()`——跨过午夜两者不是同一天，校验说没事、念出来的日期却是错的。
把 `today` 从 `verify_reply` 透传到 `written_sentence` / `summary` / `speak_date` 之后，
两处认定同一天。生产环境两者本来就一致，行为不变；测试固定「今天」，不再随日期漂。

### 验收

单测 424 → 431（`tests/test_synonyms.py` 4 条，`tests/test_facts.py` 3 条同义/精度用例）。
评测新增 2 条（`同义：账号查户号`、`同义：煤气查燃气`），全套 **38/38**，平均 4.7 s、
最长 18.9 s。两条新用例都是「存一个词、问另一个词」：宽带存「户号」问「账号」、
燃气存「户号」问「煤气」。

## 三十六、2026-11-24：提醒点开就带着任务说话（`task_id`）

§16 一直缺的那半截：点开提醒后说「完成了」「延到周五」，系统并不知道「这条」是哪条。
网页任务卡有按钮，但语音/文字里说一句就只能让模型先 `task_list` 再猜，多跑一轮 LLM（约 2 秒），
猜错还会改到别的任务上。

### 链路

```
推送 payload(code) → sw.js 存 IndexedDB（task_id/task_title）
  → 点通知：显示原文 + 绑定任务
  → 下一轮 /api/chat 或 /api/voice 带 task_id
  → Assistant._task_context_note() 注入一条 system 提示
  → 模型直接调 task_complete/task_update/task_cancel/task_postpone(task_id=…)
```

页面开着时收到 SSE 任务提醒也一样绑定；输入框上方挂一条「正在处理：交电费 ✕」，
10 分钟自动过期，也能手动取消。绑定只影响那一轮，**不写进会话历史**，否则下一句
「今天天气」还会被那段提示带着走。

说完「完成了」之后，页面会回查一次任务列表：状态变成 done/cancelled 就同时更新那张
卡片、收掉绑定条——以库里的状态为准，不靠猜模型嘴上说了什么（查不到就不动）。

### 三条边界

| 情况 | 处理 |
|---|---|
| 任务还在，状态 pending/reminded | 提示里给 id、标题、到期时间和「直接用 task_id，不要 task_list」 |
| 任务已完成 / 已取消 | 照样给状态，并要求模型如实说明，不要恢复或改别的任务 |
| 任务不存在（旧通知） | 明确告诉模型「这条已经不在了」，别拿别的任务顶 |

只注入上下文，不代执行：写操作仍走工具、`agent/guard.py` 和确认流程，声纹/客户端身份
也不因为带了 `task_id` 获得任何额外权限。

### 设备端为什么还没接

小智走 MCP `ask_xiaoma`，提醒是服务端播报出来的，没有「点击」这个动作；MCP 会话里也没有
「刚提醒过哪条任务」的记忆。硬要接，就得把「设备通道刚投递了 task 12」按设备存一份再和
`mcp:<speakerId>` 对上，而现在两边的身份并不一一对应。等反向提醒真机跑通、看客厅里实际
怎么说话再定。

### 验收

- 单测 431 → 439：绑定提示进 system、模型直接完成、缺失任务如实说明、绑定不外溢到下一轮；
  `/api/chat` 传 `task_id`、`/api/voice` 表单字段、推送 payload 带 `task_id`/`task_title`/`kind`、
  物品提醒不带任务 id。
- 评测 38 → 41 条（真模型）：`提醒：点开直接完成`、`提醒：点开改到后天`、`提醒：旧通知不乱改`。
  `case()` 新增 `bound_task`（`"latest"` 取 setup 造的那条，或具体 id）和 `not_tools`
  （断言没有多调 `task_list`、也没有改别的任务），全套 **41/41**，平均 5.1 s、最长 14.3 s。
- 前端与 SW 无法进 pytest：`sw.js` 的 IndexedDB 结构、绑定条的显示/取消要在真机上过一遍
  （锁屏收提醒 → 点开 → 说「完成了」）。

## 三十七、2026-11-24：任务卡能选延期到哪天（D17）

任务卡原来只有「延期一天」。天天点同一张卡的人，想延到周一就只能切到输入框打字；
而语音里说「延到下周一」本来就是支持的，差的只是点按这条路。

### 日期不在前端算

候选人只传 `preset`（`tomorrow` / `in_3_days` / `next_monday`），服务端用
`agent/dates.py` 的 `parse_date_text` 算日期。原因很实在：手机时区和服务器不一致、
月末、以及「周一当天点下周一是 +7 还是 +0」这三件事，各端各写一遍必然有一处错。
日期算对之后交给 `Tasks.postpone(due_at=...)`，由 `_keep_clock` 保留原时刻——
「延到明天」还是下午三点那条提醒，不会变成零点。

### 接口

`POST /api/tasks/{id}/postpone` 的 `TaskPostpone` 增加两个可选字段：

| 字段 | 说明 |
|---|---|
| `due_at` | 绝对日期 `YYYY-MM-DD`，保留原时刻 |
| `preset` | `tomorrow` / `in_3_days` / `next_monday`，服务端换算成日期 |
| `days` | 原有行为，相对当前到期日顺延 N 天 |

非法 `preset` 返回 400；任务不存在/已结束仍是 404。

### 交互

- 「延期」点一下展开四个候选：明天 / 三天后 / 下周一 / 我自己说；再点收起。
- 「我自己说」把这条任务绑到会话（`task_id`），聚焦输入框并提示「直接说『延到周五』就行」。
- 成功才锁卡片；失败只贴一行提示、按钮恢复——原来失败也会把整张卡锁死。

### 验收

- 单测 439 → 442：三个候选都保留 15:00、未知 preset 400、`due_at` 绝对日期保留时刻。
- 评测不变（41/41）：这条是点按路径，不进模型。
- 真机：手机上点「延期 → 下周一」，卡片应显示「已延期到 …」，库里 `due_at` 是下周一 15:00。

compose 注释和 doctor 的提示里都写明了怎么开。

## 四十、2026-11-26 深夜：让提醒不用先说话也能到（D78）

### 问题

D76 修完两条 bug 之后，新问题浮出来：**设备一旦空闲就断连**，提醒只能在人刚聊完那阵子送达。
早上八点提醒吃药这种，根本到不了——那就不叫提醒了。顺着日志捋出三条断点：

| 断点 | 原行为 | 后果 |
|---|---|---|
| 服务端 45 秒无语音 | 结束会话并挂断（还会让模型念一段告别） | 聊完不到一分钟就掉线 |

| 设备重启 | 开机只做 OTA，不建连 | 每次重启都要人先喊一声 |

- 服务端 `close_connection_no_voice_time: 86400`——不再挂断。

- 状态机依据：待机时 `tts start` 照样会强制进 `kDeviceStateSpeaking`；`OnIncomingAudio` 只在

## 四十一、2026-11-27：软提醒定稿，和一条开发原则

### 用户拍了三件事

1. **软硬由模型判**，不写死类型表——工具描述说清分界，用户一句话能改口。
2. **20:30 兜底**这个时点可以。
3. **兜底那句也由模型组织**，不要模板句。

设计落在 `docs/device-reminders.md` 的「软提醒」一节：分软硬 → 每轮把当天软提醒塞进
对话上下文（放在会话历史之后，避免前缀缓存失效）→ 模型自己挑话口 → 用户当场定完成/延期
→ 20:30 还没说就兜底一次（文案过模型，超时回落模板）。ROADMAP 的 D81 指过去。

### 一条开发原则（用户口述，已写进 AGENTS 与 ROADMAP §1）

> 「我可以把你当作人一样去沟通，而不是给你发送硬指令，是因为你足够聪明，而你的聪明
> 可能不止是大模型带来的，也有 agent 端的优化。」

同一个模型，编排不同，可以是「语音版命令行」，也可以是家里人。四个落点：该模型开口的
地方别替它写话；时机也是智能；不把交互写成硬指令；「活」不等于放任——`guard` / `verify` /
`confirm` 这些兜底是为了让模型敢自由说话。判断口径：想加一条「必须这样说」的规则时，
先分清它是「说得不对」还是「说得不够好」，前者写代码，后者交给模型。

### 追加：正确性优先，画像决定歧义（同日）

用户补了一条：不同的人有不同的判断规则，这正说明画像重要——记录用户的行为习惯，改善的
正是「中性、有歧义」的那类问题；确定性问题不存在这个差别。所以「说得对不对」是比「说得
自然」**更优先**的原则。已写进 `AGENTS.md` 与 `ROADMAP` §1：

- 冲突时选对的——生硬但正确，好过顺耳但错误；
- 歧义靠画像（`用户/...` 偏好层），事实不靠猜；
- 画像记习惯与偏好，不替用户做事实判断（否则就从「像个人」变成「自作主张」）。

评测那边同步改了注释：「冰箱里还有鸡蛋」这类用例的答案本就该由画像决定，评测里选一种
只是抽样，不是唯一正解——这也解释了为什么不该为某条反复调工具描述。

### 同一天：两处关键词判断交给模型

同一个取向落到代码上，去掉两处「硬指令」：

1. **内置命令预检**（`assistant._handle_command`）——以前「看看我的记忆」「忘掉酸奶」按
   关键词直接分流、不进模型，还会误伤：「取消取快递」先被当成删记忆，只是靠记忆里没命中
   才退回去。删掉关键词表，一律进 agent loop，由模型选 `memory_search` / `memory_list` /
   `memory_delete`；删除仍走确认。代价是这两类各多一轮 LLM（语音约 +2 秒）。
2. **退出命令**（小智 `exit_commands`）——以前「再见 / 拜拜 / 不聊了」在句尾命中就挂断，
   「不用再见」也以「再见」结尾，会被判成要走。现在 `exit_commands: []`，要结束时由模型

设备当时不在线，退出这条只验到「配置解析通过、服务起得来」，真机上的「再见」效果等下次

## 四十二、2026-11-27：软提醒落地（D81）

设计照 `docs/device-reminders.md` 那节走，实现时定了几个细节。

### 改了什么

1. **`tasks.mode`**（`domain/tasks.py`）：`timely` / `soft`，老库 `ALTER TABLE` 补列，
   默认 `timely`——升级后提醒时间一点不变。新增 `get_soft_due()`：今天到期或已过期的
   soft 任务，按逾期程度排序，周期任务不进（「每天八点吃药」本来就该准点响）。
   `claim_due_reminders(..., mode=)` 加一道筛选，服务端按两段调用。
2. **软硬由模型判**（`tools.py`）：`task_add` / `task_update` 多一个 `mode`，描述写清分界
   （吃药、出门、开会 → timely；牛奶过期、取快递、交水电费 → soft）。用户说「这个不用准点
   提醒」就走 `task_update` 改一行，不重建任务。
3. **注入**（`assistant._soft_reminder_note`）：每轮把今天挂着的几条软提醒（最多 4 条）
   拼成一条 system 消息，放在**会话历史之后、用户这句话之前**——每轮会变，塞进 prompt 开头
   会让前缀缓存全部失效（D58 踩过）。只给事实和编号，怎么提由模型决定；没聊到就不提。
4. **晚间兜底**（`server._scan_once`）：`SOFT_REMINDER_LAST_CALL`（默认 20:30）之前，
   soft 任务和物品都不进 `claim_due_reminders`；到点之后才按原通道投递（设备 → 网页 → push），
   文案走 `Assistant.SOFT_REMINDER_PROMPT`（像忽然想起来），失败/超长/没说对名字回落模板。

### 实现时定的三条

- **物品到期也算 soft**。`items` 没有也不会加 mode 列：物品只有一个日期，没有「到点」
  可言。所以物品和 soft 任务同一道门，20:30 前不领取。代价是物品提醒从「当天任意时刻」
  挪到晚上；换来的是白天不再突然播报——这正是用户要的。
- **注入上限 4 条，物品过期超过 7 天不再提**。没人删的过期牛奶每轮都在耳边念，比不提
  更烦。任务不设这个上限：欠了十天的账单还要提。
- **注入不进会话历史，也不进热点上下文**。它属于「这一轮看得到的事实」，下一轮重新算；
  写进历史会让模型以为已经提过（会话历史是它判断「说没说过」的依据）。

单测 697 通过（新增 19 条：mode 存取/筛选/改口、注入内容与位置、晚间门控、软语气）。

### 还没验的

真机上的效果——设备待机时麦克风是关的（D78），用户不开口就没有「对话中」，
软提醒只能等下一次聊天；这条在设计里写了，不是这次能解决的。等设备上线后要看的：
①聊到牛奶时它会不会顺口提；②白天确实不再有物品播报；③20:30 之后没提过的会补一次。

## 四十三、2026-11-27：软提醒上线 + 门锁提醒说清「谁怎么开的门」

### 部署

镜像重建（`docker compose up -d --build`），容器 healthy；`/data/tasks.db` 启动时
自动补了 `mode` 列，老任务全部 timely。软提醒从这一刻起在真实服务里生效。

### 门锁提醒

用户反馈：门锁的提醒只是「门锁提醒」，没有具体内容——谁、用什么方式、门内开锁，
一概没有。查了真实数据，小米官方集成把 MIoT `lock-event` 的参数原样放在事件属性里：

```
event.loock_..._lock_event_e_2_1020
{"锁动作": 1, "操作方式": 16, "操作位置": 3, "操作ID": 0}   # 关门后的自动上锁
```

对照 `loock.lock.t3pul`（小米智能门锁 2 Pro）的 MIoT spec 翻译：

- 操作方式：手机 / 指纹 / 密码 / NFC / 人脸 / 指静脉 / 掌纹 / 机械钥匙 / 一次性密码 /
  周期性密码 / HomeKit / 胁迫 / 双重验证 / 转盘 / 手动 / 自动
- 锁动作：上锁 / 开锁 / 上提加固 / 反锁开与关 / 童锁开与关 / 离家模式开与关
- 操作位置：门内 / 门外 / 无法区分；操作ID 是锁上的用户编号

于是同一条事件现在念成「妈妈用指纹开了门」「门从里面打开了」「危险：爸爸用胁迫方式
开了门，注意安全」。

三个判断：

1. **自动上锁不播报**——每次关门都跟着一条，念出来全是噪音；以前它其实被 10 分钟
   事件冷却顺手挡掉了。`describe_lock_event` 返回空串表示「看懂了但不用说」。
2. **门锁不走 10 分钟事件冷却**（`HOME_LOCK_COOLDOWN_SECONDS`，默认 0）。那条冷却是
   给摄像头移动侦测的；套在门锁上等于「10 分钟内进第二个人不报」，正好吞掉安全提醒。
   重复上报本来就靠时间戳去重。
3. **位置不确定就不猜**：操作位置=3 时说「门被手动打开了」，不说「有人在门外」。

### 补：读了三天真实事件，把凭据编号搞清楚了

用户提醒「开锁有面容和指纹」，于是去读 HA 的 history（不能只看当前 state，那条是
最后一次自动上锁）：三天 41 条，去重后五种组合——

| 组合 | 次数 | 念成 |
|---|---|---|
| `锁动作=1 操作方式=16 位置=3` | 24 | （静默）自动上锁 |
| `锁动作=2 操作方式=16 位置=1` | 8 | 门从里面打开了 |
| `锁动作=2 操作方式=5 位置=2 操作ID=2004` | 4 | 2004 号用户刷脸开了门 |
| `锁动作=2 操作方式=5 位置=2 操作ID=2001` | 1 | 2001 号用户刷脸开了门 |
| `锁动作=2 操作方式=2 位置=2 操作ID=501` | 2 | 501 号用户用指纹开了门 |

两件事因此确定：

- **操作ID 是凭据编号，不是家庭成员编号**：面容是 2001/2004 这种四位数，指纹是 501，
  同一个人的人脸和指纹是两个号。所以 `HOME_LOCK_USERS` 按凭据写
  （`501=爸爸,2001=爸爸,2004=妈妈`），配置里已按实测编号改示例。
- **门内开锁就是 `位置=1`、`操作方式=16`**，不用猜；`位置=3` 的自动上锁按既定规则静默。

面容文案用「刷脸开了门」（原来按 spec 写「用人脸」，念着别扭）。

### 再补：异常事件与门状态

用户要求「异常事件和门状态的门未关/门虚掩都提醒」，于是：

- `describe_lock_exception()` 翻译 26 个异常码（撬锁、有人撬门、频繁开锁失败、门锁被重置、
  钥匙未取出、门一直没上锁、离家后门内开锁、各类故障、电量低…）。
- **23 门未关 / 24 门虚掩不在异常事件里念**，交给门状态传感器——同一件事报两遍比不报还烦。
