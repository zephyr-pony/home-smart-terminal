# 2026-11 变更说明（护栏 / 任务闭环 / 控制台）

这一轮从「本地小模型能不能用」开始，最后落成了三层东西：**写操作的确定性护栏**、**任务通知闭环**、**控制台的可用性**。设备端联调时这份文档够用来对接口和避坑。

对应提交：`a4552d9` … `e84efa4`（12 个），测试从 154 涨到 214。

---

## 一、为什么要做护栏

用 Spark-X2.6-4B（本地）和 aisp 的 DeepSeek-V4.1-Flash 跑同一组用例，暴露的问题不是「答得不好」，而是**写错数据**：

| 现象 | 实测 |
|---|---|
| 凭空补到期日 | 「冰箱里还有三个鸡蛋」约一半概率被记成今天/12-21/12-31 到期 |
| 相对日期算错 | 「牛奶下周三过期」4B 稳定算成周四（正确是 11-25） |
| 查询被当成写操作 | 「我家水费户号是多少」调用 `task_add`，造出一条不存在的交电费提醒 |
| 假确认 | 没调任何写工具，却回「已经记在清单里了」，库里一条都没有 |

提示词约束不住（在系统提示里写「查询不得顺带写入」，重跑三次照旧），所以改成**编排层的确定性校验**。

## 二、五道防御（对所有模型生效，除注明外）

| # | 机制 | 位置 | 作用 |
|---|---|---|---|
| 1 | 中文日期解析 | `agent/dates.py` | 「明天/下周三/三天后/周末/11月25日/下午三点」→ 具体日期，交给代码算 |
| 2 | 写参数护栏 | `agent/guard.py` | 日期以原话为准；句子无日期线索则留空；`task_add` 标题在原话里找不到依据则整次拒绝 |
| 3 | 参数校正提示 | `agent/guard.py` `correction_note` | 把校正结果附在工具返回里，减少模型口播旧值 |
| 4 | 写操作确认 | `agent/confirm.py` | `CONFIRM_WRITE_ACTIONS` 控制，复述参数后再落库（默认关闭） |
| 5 | 假确认拦截 | `agent/guard.py` `guard_false_claim` | 非疑问句 + 无写工具执行 + 回复声称已完成 → 换成诚实说法 |

设计取舍：第 1–3 条无条件生效，换模型时行为不变；代价是偶尔用代码判断覆盖模型，所以日期线索词表要持续补（「年底/过几天/周末」等 12 个是踩出来的）。

### 配置

```
CONFIRM_WRITE_ACTIONS=0        # 关闭（默认，大模型直接用）
CONFIRM_WRITE_ACTIONS=1        # 四个写工具全部先确认
CONFIRM_WRITE_ACTIONS=tasks    # 只确认 task_add（误提醒代价最高）
CONFIRM_WRITE_ACTIONS=item_add,task_add   # 显式列表
```

开启后同时启用第 5 条。**决定用本地模型时必须打开**，否则写操作等于裸奔。

## 三、任务通知闭环

### 新增工具

| 工具 | 语义 | 备注 |
|---|---|---|
| `task_update` | 改标题/时间/类型 | 至少改一项；标题须在原话里有依据 |
| `task_cancel` | 标记 cancelled，不删记录 | 保留审计 |
| `task_postpone` | 改到指定日期 | **「明天」「下周一」是目标日期，不是「到期日 +N 天」**；说不出具体日期才退化成顺延 N 天 |

⚠️ 第 3 条的语义是实测后修正的：第一版把「明天」当成 +1 天，结果把「明天到期」的任务推到了后天。

### 接口

```
POST /api/tasks/{id}/postpone   {"days": 1}   →  {"ok": true, "task": {...}}
```

延期必须**清 `reminded_at` 并把 status 退回 `pending`**，否则冷却窗口会挡住，延期后再也不提醒（`Tasks.postpone` 已处理）。

### 提醒卡片

页面在线时，SSE 的任务提醒渲染成卡片，带「完成 / 延期一天 / 取消」三个按钮，直接打上面的接口。

- 按钮不持久化：聊天历史只存文字（和语音播放按钮一致）
- **Web Push 仍是纯文字**：推送正文不发交互，从系统通知点进来看到的是文字版本

### 澄清规则修正

「交电费的提醒不用了」原来会被澄清引擎拦住，反问「是哪里的电费」，导致**取消电费提醒永远走不通**。现在取消类说法（不用了/取消/算了…）直接放行，新建账单仍然会追问。

## 四、数据正确性

### 同名物品合并

`item_add` 的去重只在 5 分钟提案窗口内、且名称+日期都要一致。一周里说两次「牛奶下周三过期」会变成两条记录、两次提醒。

现在 `ProposalService.add_item` 合并同名物品：

| 情况 | 行为 |
|---|---|
| 带新日期 | 更新到期日，清 `reminded_at`、状态退回 `active` |
| 不带日期 | 保留原值，不抹掉已知日期 |
| 已经过期 | 不动旧记录，新建一条（保留历史） |

审计里记为 `merged`。

### 记忆检索兜底

`memories_fts` 只索引 `summary`，原文独有的词（号码、品牌、补充说明）查不到，助手会回「我没记过」——其实记过。

现在 FTS 未命中时用 `LIKE` 扫 `summary + text` 补召回，`%` 和 `_` 已转义。实测漏召的 `0571`、`南孚`、`贴在门口`、`每周三` 全部恢复。

## 六、已知限制

1. **4B 口播旧值**：落库数据正确，但模型仍可能照着旧参数说话（库里 11-25，嘴里 11-26）。`correction_note` 只能缓解，不能保证。
2. **假确认不能 100% 拦截**：规则是保守的（疑问句、无写工具、有完成表述），边界场景仍会漏。
3. **Web Push 无交互**：要按钮只有页面在线那条路径。
4. **多轮指代弱**：本地 4B 对「那还剩几天」这类指代会反问，aisp 正常。
5. **日期线索词表是穷举**：没收录的说法会被当成「没有日期线索」，护栏会清空模型给的日期。遇到误伤就往 `agent/dates.py` 的 `_DATE_HINT_RE` 里补。

## 七、给设备端的注意点

- 语音入口建议只暴露：`family_search`（查）、`task_add`（记提醒）、`task_complete` / `task_postpone` / `task_cancel`（操作提醒）
- 写操作一律走确认（本地模型开 `CONFIRM_WRITE_ACTIONS=1`），客厅场景一句「要记成…确认吗」比事后纠错便宜
- 延期的说法直接传原话即可，天数由服务端换算，不要让设备端算日期
- 若将来做 aisp → 本地自动降级：**降级时必须同时切弱模型模式**（D29）

## 八、2026-11-23：对外话术统一（`agent/wording.py`）

写操作的三处文案——确认句、确认后的回话、执行回显——原来各写一遍，日期格式不一致。
最难看的是确认之后：回话直接用了工具返回的原始串

```
已添加物品：牛奶，到期日 2026-12-02
```

TTS 会念成「二零二六 杠 十二 杠 零二」。确认的意义是让人当场发现参数错了，
念成一串数字等于没确认。

现在统一由 `agent/wording.py` 生成：

| 场景 | 现在说的话 |
|---|---|
| 写入确认 | 你说的「牛奶下周三过期」，要记成：牛奶，12月2日（周三）到期。回复「确认」或「取消」。 |
| 确认之后 | 已记好：牛奶，12月2日（周三）到期。 |
| 直接写入的回显 | 牛奶，12月2日（周三）到期。（只在参数里有日期、且模型回复没提到时补） |

三条规则：日期说「12月2日（周三）」或「明天」，有时间说「下午3点」不说「15:00」，
确认句引用用户原话（人记得自己说了什么，比记得参数格式可靠）。

顺带修了一个**会随时间变红的测试**：`test_confirm_writes_and_keeps_guarded_args`
把「下周三」写死成 `2026-11-25`，换一天跑就失败（今天是 11-23，下周三其实是 12-02）。
改成用 `parse_date_text` 现场推算。

测试 266 → 280。真模型实测：

```
问：牛奶下周三过期（确认模式）
   你说的「牛奶下周三过期」，要记成：牛奶，12月2日（周三）到期。回复「确认」或「取消」。
确认后：已记好：牛奶，12月2日（周三）到期。
库里：牛奶 2026-12-02
```

## 九、2026-11-23：删除只删该删的（`Items.delete_exact` / `_resolve_delete`）

`item_delete` 原来是 `LIKE %名字%` 之后**全删**：清单里同时有「酸奶」和「酸奶机」时，
说一句「删掉酸奶」会把两台机器都删掉。删除不可逆，这种模糊匹配迟早出事。

现在删除前先坐实目标（`assistant._resolve_delete`）：

| 情况 | 行为 |
|---|---|
| 有精确同名 | 直接确认「确认删除物品「酸奶」吗」 |
| 只命中一条相似项 | 用它的全名确认（「牛奶」→「蒙牛牛奶」），用户能看出认错了 |
| 命中多条 | **不删**，列出名字问要删哪个，直接结束本轮 |
| 一条都没有 | **不删**，明说「没有找到，什么都没删」 |

后两种情况刻意不把结果交回模型转述——它会顺势说成「已经删掉了」。
记忆删除同理：零命中不进确认，多条命中在确认句里报条数。

真模型实测（清单里有 酸奶 / 酸奶机 / 酸奶大瓶）：

```
删掉酸奶 → confirm：确认删除物品「酸奶」吗？回复「确认」或「取消」。
删掉牛奶 → chat：没有找到「牛奶」这个物品，什么都没删。
清单：酸奶大瓶、酸奶机、酸奶   ← 一个都没少
```

测试 282 → 292。

## 十、2026-11-23：记忆摘要只能用原话里的字（`summary_grounded`）

记忆存「原文 + 摘要」，摘要进 FTS 索引。工具描述原来让模型「相对时间转绝对日期」，
于是实测出现：

```
原话：明天买电池
摘要：8月9日买电池      ← 模型自己换算的日期，还错了
```

`is_grounded` 拦不住它——判据是「至少一个二元组重合」，两句共享「买电」「电池」。
它适合判断「这个话题用户提过没有」，不适合判断「这句话是不是原话剪出来的」。

现在摘要用**子序列判据**（`agent/guard.py` 的 `summary_grounded`）：摘要里的每个字
都必须能在原话里按顺序找到，允许跳过字。摘要的本职就是把原话剪短，所以「只删不加」
就是它的定义。校验不过时：

| 处理 | 原因 |
|---|---|
| 摘要换成原话，**记忆照记** | 记忆是用户的真实陈述，摘要是可降级的 |
| 工具返回附一句校正说明 | 免得模型接着口播那个编造的日期 |

不拒收整条记忆：为了模型的格式错误丢掉用户的真实事实，是本末倒置。摘要变长只影响
索引体积，FTS 全文召回反而更好。

真模型实测（摘要都是原话剪出来的，没触发降级）：

```
原话：上周六去医院复查血压，医生说还行
摘要：上周六复查血压，医生说还行      只删不改=True
```

测试 292 → 298。

## 十一、2026-11-23：回复发出前过事实校验（`agent/verify.py`）

护栏和 `correction_note` 保证的是**库里**对，用户听到的却是模型那一句。实测模型能在
同一个回复里一边写对一边念错：参数校正成 12-02，嘴里仍说「11月25日过期」；
或者说成「12月2日（周四）」（那天是周三）。语音没有回看的机会。

现在最终回答发出前过一遍 `verify_reply`：

| 回复里的内容 | 判据 |
|---|---|
| 具体日期（12月2日 / 12月2号 / 2026-12-02） | 必须是这次写进去的那天（今天是例外，允许用作上下文） |
| 相对词（明天/后天…） | 换算成日子后再比 |
| 周几（下周三） | 带「下/本/这」的按整句解析，比具体日期 |
| 周几（周三） | 只比星期几——口语本来就会省「这周」 |
| 引号里的名字（「酸奶」） | 必须在用户原话或工具参数里出现过 |

不一致就**整句**换成 `wording.written_sentence` 拼的模板句，不修补也不拼接——
一段话里一句对一句错，比整句朴素更难发现。

配套改了两处：

1. **写完之后那轮不走流式。** 逐字推给设备的片段收不回来，校验失败也没法纠正。
   有写入时最终回答等校验完再一次性下发，第一轮（只吐 tool_calls）仍然流式。
2. **改期保留原时刻。** 真模型探针发现「取快递改到后天」把 15:00 改成了 00:00，
   模型却还说「下午3点」——库错了，校验再准也救不了。`domain/tasks.py` 的
   `_keep_clock`：只给日期时沿用原时刻，原话带了时间才覆盖。

真模型实测（第二轮回答故意换成错日期）：

```
模型原话：好，记好了，牛奶后天就过期。
实际回复：已记好：牛奶，12月2日（周三）到期。
库里：牛奶 2026-12-02
```

正常路径不误杀：

```
牛奶下周三过期   → 牛奶，12月2日（周三）到期。记好了，牛奶12月2号（下周三）过期…
明天下午三点取快递 → 取快递，明天下午3点。好，明天（11月24日）下午三点提醒你取快递。
取快递改到后天   → 取快递已经改到后天（11月25日）下午3点了。   库：2026-11-25T15:00
```

测试 298 → 317。

## 十二、2026-11-23：事实留失效史（`Facts.store` / `valid_to`）

`facts` 表一直有 `valid_from` / `valid_to` 两列，但从来没用过：`store` 每次都直接
`INSERT` 新行，旧行既没关闭也没删除。于是同一个户号存过几次就有几条「当前有效」，
检索时新旧值一起返回，模型挑哪条看运气。真实库里的样子：

```
id=1 爸妈家·电费户号 123456  valid_to=NULL
id=4 爸妈家·电费户号 123456  valid_to=NULL
id=5 爸妈家·电费户号 123456  valid_to=NULL
id=6 爸妈家·电费户号 123456  valid_to=NULL
```

现在：

| 情况 | 行为 |
|---|---|
| 值没变 | 沿用现有记录，不堆行（重复说同一件事很常见） |
| 值变了 | 旧行 `valid_to=现在`，新行 `valid_from=现在`，返回 `replaced` 让回话能说「原值已失效」 |
| 检索 | 默认只返回 `valid_to IS NULL`；`include_history=True` 或 `history(subject, predicate)` 看历史 |
| 旧库 | 启动时 `_close_legacy_duplicates` 把同主体+属性的多条有效记录关到只剩最新一条，幂等 |

不选「直接覆盖」：覆盖之后「以前是多少」就查不到了，而户号、地址、型号恰恰会变。
也不选「只插新行」——那正是现在的问题。

在真实库的副本上验过：6 行 → 3 条有效（爸妈家 / 家 / 户号 三个不同主体）+ 6 条历史；
再存一次新值，有效数不变、历史变 7。

测试 317 → 321。

## 十三、2026-11-23：MCP 接入点，`_meta` 声纹透传实测通过

### 先纠正一个方向

之前 ROADMAP 里写的是「写一个 `scripts/mcp_xiaoma.py`，出站连小智的接入点」。
读小智源码后确认方向**反了**：小智服务端才是 MCP 客户端，它出站连我们。

```
设备 ──语音──▶ xiaozhi-server ──MCP(WebSocket, 出站)──▶ 小马 /mcp_endpoint/mcp/
```

依据：`core/providers/tools/mcp_endpoint/mcp_endpoint_handler.py` 里
`websockets.connect(mcp_endpoint_url)`，然后发 `initialize` / `tools/list` / `tools/call`。

### 协议形状（按源码实现，没用官方 SDK）

- 裸 JSON-RPC 2.0，transport 是 WebSocket；`protocolVersion` 为 `2024-11-05`
- id 固定：`initialize=1`、`tools/list=2`、`tools/call` 从 3 开始
- 工具返回值只读 `result.content[0].text`，`isError: true` 表示失败
- 小智会忽略官方 SDK 的很多能力，用 SDK 反而要垫一层

新增 `adapters/mcp_endpoint.py`，`server.py` 加路由 `/mcp_endpoint/mcp/`：
只暴露一个工具 `ask_xiaoma(text)`，交给 `assistant.process_text`。

### `_meta` 透传：实测通过

小智把声纹识别结果放在 `tools/call` 的 `params._meta`：

```json
{ "speakerId": "spk-dad", "speakerName": "爸爸" }
```

未命中时整个 `_meta` 不出现。探针按同样的报文形状跑真实服务（不是 mock）：

```
① initialize → protocolVersion 2024-11-05
② tools/list → ask_xiaoma
③ tools/call → 你好呀！我是小马，家里的事都可以交给我记～
服务端日志：🔊 MCP 声纹身份：speakerId=spk-dad name=爸爸
```

不带 `_meta` 时日志没有这一行，会话落在 `mcp:device`；token 错误握手 403。

身份怎么用：**只分会话上下文**（`client_id = "mcp:<speakerId>"`），不认「这是谁」，
不参与鉴权，写操作照样走提案/确认。`speakerId → persons` 的归属留给 D40。

### 配置与文档

- `.env` 新增 `MCP_TOKEN`，留空则接入点整体关闭（它能写库，不能默认对外）
- `scripts/mcp_probe.py`：不需要硬件，按小智报文形状验证整条链路
- `docs/xiaozhi-mcp.md`：方向、报文、配置、实测记录

## 十四、2026-11-23：反向提醒的方案定了（D42，方案 A）

问题是「提醒能不能主动推给客厅设备」。查完小智源码，结论是方向不对称：

- 设备 → 小马：可以，MCP `tools/call`
- 小马 → 设备：**不行**。小智对 MCP 入站消息只处理 `result`/`error`，
  收到 `method` 只打一行日志；xiaozhi-server 也没有「让设备说话」的 HTTP 接口或定时任务；
  设备连接句柄藏在 `ConnectionHandler` 里，没有全局注册表

所以主动提醒只能由**持有设备连接的那一侧**发。三条路比过之后定 A：

| 方案 | 改什么 | 工作量 | 结论 |
|---|---|---|---|
| A | fork `xiaozhi-server`：连接注册表 + 订阅小马 SSE + 调它现成的 `speak_txt` | 1–2 天 | **选它** |
| B | 设备直连小马，自己重写语音主循环（VAD/ASR 流式/TTS 流控/打断） | 1–2 周起 | 远期 |
| C | 常开平板挂网页，SSE 已能弹卡片并播报 | 0 | 过渡可用 |

固件不动：B 的工作量也不在固件，而在服务端。fork 的改动集中在三个钩子，
升级冲突面小，真有必要还能做成通用接口提 PR 上游。

落地清单、接口契约、验收步骤（数字人测试页可代替硬件）写在
[`device-reminders.md`](device-reminders.md)。本日只记录决策与方案，代码未动。

## 十五、2026-11-23：服务器迁移清单 + 硬件前准备清单

### 服务器迁移（`docs/server-migration.md`）

按「前置体检 → 装系统 → 依赖与服务 → 数据迁移 → 网络地址 → HTTPS → 验收 → 回滚」
拆成可勾选步骤。补了 §22 里没写到的几件事：

- **xiaozhi-server 也要搬**：它在仓库之外（`D:\xiaozhi-server`），有独立的 `.config.yaml`
  和 `model.pt`，容易漏
- Linux 上没有 `host.docker.internal`：要么 `extra_hosts: host-gateway`，要么 host 网络
- HA 容器在 Linux 上改回 `network_mode: host`
- 换地址后**推送订阅和 PWA 全部绑定旧源**，每台手机要重新开启
- 迁移前用 `sqlite3 .backup` 做一致性快照，不要在服务运行时直接拷 db
