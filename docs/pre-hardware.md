# 硬件到位前的准备清单

ESP32 到货前能做的、必须做的、以及「等硬件再说」的分开列。按「是否卡住真机验收」排优先级。

现状（2026-11-23）：服务端与 Web 控制台已可用；小智服务端在本机 Docker 跑过，
MCP 接入点与 `_meta` 已验证；**反向提醒（服务端→设备）还没做**；手机推送受 HTTPS 限制。

## P0：不做就会在真机前卡住

### 1. 反向提醒（方案 A）

- 为什么：MCP 只能设备→小马，提醒到不了客厅音箱。没有它，设备只是一问一答。
- 做什么：`docs/device-reminders.md` 的清单（小马侧 4 处 + 小智 fork 3 个钩子）
- 无硬件可验：数字人测试页就是设备连接
- 依赖：无

### 2. 延迟目标：现在差得很远

2026-11-23 复测（aisp `DeepSeek-V4.1-Flash`，本机 xiaozhi + 假设备，4 句）：

| 场景 | ASR | 首句 | 整轮 |
|---|---|---|---|
| 闲聊「你好小马」 | 843 ms（冷启动） | **4.2 s** | 9.1 s |
| 查询「我记了哪些东西」 | 172 ms | **6.3 s** | 15.3 s |
| 写入「明天下午三点提醒我取快递」 | 234 ms | **7.9 s** | 13.3 s |
| 设备「客厅灯开着吗」 | 172 ms | **6.3 s** | 14.5 s |

分段计时（同一套代码，内存库，不含 TTS）：

| 场景 | 决策轮 | 工具 | 回答轮首字 |
|---|---|---|---|
| 闲聊（单轮） | — | — | 1.6 s（总 2.7 s） |
| 查询 | 1.8 s | 0.02 s | 2.4 s |
| 写入 | 2.5 s | 0.00 s | 2.6 s（非流式） |
| 设备查询 | 2.7 s | 0.02 s | 1.5 s |

TTS 单句约 1.9–2.2 s（Edge TTS，整句合成）。

结论：**带工具的一轮要多一次决策调用**，这 1.8–2.7 s 是结构性成本；回答轮首字再 1.5–2.6 s；
TTS 1.9 s 左右。目标 3 s 在现结构下只有闲聊接近。

可选的压法（按性价比）：

1. **写操作跳过第二轮 ✅ 2026-11-23 已完成**：工具结果已经有了，直接用 `wording.written_sentence` 回话。
   写入首句 7.9 s → **4.1 s**，整轮 13.3 s → 9.6 s；闲聊 4.2 → 3.4 s（同一次冷热波动），
   查询不变（6.4 s）。只在「整轮都是成功写操作」时短路；混了查询、工具失败或被护栏拦下仍交给模型
2. **读查询前置确定性路由**：命中「几号/清单/开着吗/余额」就直接跑一个工具，再单轮生成。
   省 1.8–2.7 s；风险是路由不准，必须能回退到 agent loop
3. **TTS 按句流式**：xiaozhi 已支持按句，回复越短首句越快；prompt 里已有「简短」要求
4. 换模型路由：官方 `deepseek-flash` 的 TTFT 0.6–1.0 s，但当前决定不做分流
5. 砍上下文 / 裁工具 schema：0.3–1 s，收益有限

要做的事：

- [ ] 定验收线（建议：P95 闲聊首句 ≤ 3 s、工具查询 ≤ 5 s、写入 ≤ 5 s）
- [x] 第 1 条（写操作跳过第二轮）已完成：写入首句 4.1 s
- [ ] 评估第 2 条（读查询前置路由）：查询仍 6.4 s，这是下一个大头
- 待决策：D43（验收线本身还没拍板）

### 3. 唤醒词与固件变体

- 固件用 ESP-SR 的 WakeNet，内置唤醒词是「你好小智」这类；叫「小马」大概率要**自定义唤醒词模型**
  （Espressif 有定制服务/工具链），不是改一行配置。
- 要在下单和刷机前定：用内置唤醒词、还是做「小马」模型、还是先双唤醒词过渡。
- 同时定 OTA/WebSocket 地址（局域网 IP 还是域名）——它和服务器迁移耦合。
- 待决策：D44

### 4. 硬件选型与下单（D23）

- [ ] 定「先买成品小智」还是「ESP32-S3 + 麦克风阵列板」
- [ ] 核对固件支持列表：ESP32-S3、16 MB flash、8 MB PSRAM、麦克风阵列/扬声器
- [ ] 确认供电、外壳、是否要 AEC 参考回采（打断体验取决于它）
- 无硬件可做：只做选型和下单，没有别的

### 5. HTTPS（手机推送与「添加到主屏」）

- 现在只有 `localhost` 是安全上下文；手机用 `http://<LAN IP>:8200` 会同时失去推送和 PWA。
- 方案见 `docs/server-migration.md` 阶段 5；选 Caddy 本地 CA 还是 Tailscale。
- 不解决也能靠设备提醒，但「人不在客厅」时手机就收不到。

## P1：真机前应该做，但不会卡住验收

### 6. 设备端的写操作确认粒度

- `CONFIRM_WRITE_ACTIONS` 是全局开关：开了之后网页每次写也多问一句。
- 客厅场景建议开（一句「要记成…确认吗」比事后纠错便宜），但要确认网页侧能否接受。
- 若不能接受，需要按通道区分（`mcp:` 开、网页关），这是新配置项，别偷偷改语义。

### 7. 声纹身份只到「分会话」这一层

- `_meta` 已验证；现在只用于 `client_id = mcp:<speakerId>`。
- 要叫得出名字、按人隔离记忆，需要 `persons` + `owner`（D40）。可以在设备到位后再做，
  但「谁在说话」的日志最好现在就开始攒（已有 `🔊 MCP 声纹身份` 日志）。

### 8. 小智服务端与 MCP 的联调收尾

- 小智配置里 `mcp_endpoint` 指向小马、`mcp_forward_speaker: true`
- 用数字人页跑一遍：普通闲聊、记提醒、查询、设备控制、打断
- 这一套和反向提醒共用同一个进程，先跑通再打补丁

### 9. HA 还欠一次真实事件验证

- Docker Desktop 当前没起，事件订阅在退避重连
- 门铃/门锁事件只验过传输层（0.46 s），没做过真实触发
- 顺便把「HA 常开」写进运维：开机自启、容器 `restart: unless-stopped`

### 10. 小修小补（低风险，别拖成习惯）

- [ ] 口播时间校验：现在只校验日期，模型仍可能把 15:00 说成 20:00

      网页侧的展示逻辑要确认一下是不是漏了
- [ ] 评测集：20–30 句固定输入（唤醒/不唤醒、记提醒、改期、删除、查询、设备、歧义、数字），
      每次改编排跑一遍，别只靠手点
